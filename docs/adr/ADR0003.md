# ADR-0003 — Store Step State Using a Hybrid Relational and JSONB Model

## Status

Accepted

## Context

The onboarding flow must be resumable. Each step has different data:

* Details: company name, account id, API key presence.
* Validation: status, items, warnings, invalid reason, transient failure details.
* Review: confirmation/go-live readiness.

A fully relational schema would provide strong database constraints, but it would require schema changes for every future step or payload change. A fully schemaless model would be flexible but would hide important lifecycle constraints.

PostgreSQL supports JSONB, which allows a hybrid model.

## Decision

Use a hybrid relational + JSONB persistence model.

Core lifecycle and identity are relational:

* onboarding session
* current step
* session status
* step key
* step status
* timestamps
* uniqueness constraints
* partner account uniqueness

Step-specific data is stored as JSONB payloads in `onboarding_step_state`.

Provider validation attempts are stored separately for audit/history.

## Intended Tables

```text
onboarding_session
- id
- current_step
- status
- created_at
- updated_at
- completed_at
```

```text
onboarding_step_state
- id
- session_id
- step_key
- status
- payload jsonb
- created_at
- updated_at
- completed_at

unique(session_id, step_key)
```

```text
provider_validation_attempt
- id
- session_id
- attempt_number
- account_id
- request_fingerprint
- outcome
- response_payload jsonb
- error_message
- started_at
- completed_at
```

```text
partner_account
- id
- session_id unique
- company_name
- status
- went_live_at
- created_at
```

## Rationale

This design keeps the business lifecycle explicit while allowing step payloads to evolve.

The unique constraint on `(session_id, step_key)` supports idempotent step submission.

Separate validation attempts preserve auditability without confusing historical attempts with the latest resumable validation state.

## Type Safety Strategy

The application should not pass untyped maps through the codebase.

Each step payload should have a typed Kotlin DTO, for example:

* `DetailsPayload`
* `ValidationPayload`
* `ReviewPayload`

The service layer validates and serializes/deserializes these DTOs.

A future implementation may add versioned JSON Schema validation for payloads.

## Tradeoffs

### Benefits

* Flexible step payloads.
* Clear lifecycle constraints.
* Good fit for PostgreSQL.
* Supports future steps without schema churn.
* Clean separation between latest state and validation history.

### Costs

* Fewer database-level constraints inside payloads.
* Requires application-level validation.
* Queries into payload fields are less straightforward.
* Payload versioning must be handled intentionally if schemas evolve.

## Consequences

Repositories will serialize and deserialize JSONB payloads.

Tests must cover payload round-trips and state reconstruction.

Future schema evolution should consider payload versioning and JSON Schema validation.
